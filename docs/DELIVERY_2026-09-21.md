#### The round trip, reproduced

Not inferred. I ran the real parser (`backend/app/core/template_io.py::parse_upload`)
against the real export format (`backend/app/inventory/export.py::items_to_csv`):

```
ERRORS: ['Row 4: "Name" is required; "Unit" is required']
ROWS  : []
```

**The export's own totals footer is what rejects the file.** `items_to_csv`
writes a title row, a blank, the headers, the data, a blank, and then
`["", "", "", "", "", "Total stock value", "70.00", "", "32.50"]`. The parser
skips fully blank rows but not that one, finds an empty Name and Unit, and
fails the entire upload — 422, nothing imported. That is literally "inventory
import refused its own export".

Two more faults hide behind it. Deleting the footer by hand and re-running:

```
ROWS: [{'name': 'Basmati Rice', 'category': 'Dry Goods', 'unit': 'kg',
        'supplier': '* Fresh Farms'}]
```

- **The stock quantity is silently gone.** The export's header is `In stock`;
  the template's column is `Opening stock` with aliases `stock, quantity, qty,
  opening`. "in stock" matches none of them, so the column is dropped without
  an error. A restaurant importing its inventory gets its items with **zero of
  everything** — and the screen looks like it worked.
- **Every supplier link breaks.** `export.py::_supplier` prefixes the chosen
  vendor with `★ `. `inventory/router.py::_find_vendor` matches on an exact
  case-folded name, so `★ Fresh Farms` never finds `Fresh Farms`. Every row is
  reported as a missing supplier.

So even a "fixed" round trip that only removes the footer would move his
inventory across with no quantities and no suppliers. This is why 48.2a needs
a designed format contract, not a patch.

## 3 · RISK — WHAT GOES WRONG, PER TASK

### 3.1 · Task 4, MIGRATION (48.3)

Moving a hotel touches every table with a `hotel_id`, and the schema has three
tables that do not use that column at all (`chats.hotel_a`/`hotel_b`,
`chat_messages.sender_hotel_id`). Any code assuming `hotel_id` everywhere is
already wrong — that assumption caused a real outage and it is why
`deletion.py` reads the FK graph at runtime instead.

**Failure modes, worst first:**

1. **A copy that half-remaps its foreign keys.** In 48.3b every row gets a new
   id and every FK between copied rows must be repointed in the same pass. Miss
   one and the new hotel's recipe references the SOURCE hotel's ingredient. It
   does not error. It does not look broken. It is a cross-tenant data link that
   will surface months later as "why did my ingredient price change". This is
   the single worst outcome in the whole batch and it is silent — so the
   acceptance test must be an explicit scan for any FK in the new hotel's rows
   pointing at a row owned by another hotel, not a visual check.
2. **Split ownership.** A MOVE is (a) attach the target user, (b) repoint
   ownership, (c) revoke the old. Half-run leaves two owners or none. Must be
   one transaction — and note the documented trap: `audit_service.record()`
   **COMMITS internally**, so calling it mid-transaction splits the very
   transaction that must be atomic. Audit after the commit, as
   `delete_hotel` already does deliberately.
3. **S3 documents.** Upload keys are `{hotel_id}/{doc_id}/{filename}`
   (`infra/s3.tf`). A COPY that reuses the source keys gives two hotels one set
   of files — and deleting one hotel then deletes the other's documents. Either
   copy the objects under the new prefix or the copy is not a copy.
4. **Things that must NOT travel.** `assistant_threads`/`assistant_messages`
   hold the source hotel's private conversations; copying them to a new owner
   is a data leak dressed as a feature. Same for `audit_events` (whose actor
   emails belong to the old company) and `ai_usage` (whose cost is already
   attributed and billed). Decide the exclusion list explicitly and write it
   down; the default must be EXCLUDE, not include.
5. **Uniqueness collisions.** `hotels.username` is the public handle and
   `users.email` is unique. A copy needs a new handle generated and checked,
   not derived.
6. **An invitation that never expires.** 48.3e's two-party accept creates a
   pending state. Without an expiry you accumulate live invitations that can
   transfer a business a year after everyone forgot.

**What must be atomic:** the ownership swap and the revocation, together.
**What must NOT be inside that transaction:** email sends, S3 object copies,
audit records.
**Rollback:** for MOVE, deactivate the old owner rather than delete it, for a
stated window (14 days), so reversal is a flag flip and not a restore. For
COPY, rollback is "delete the new hotel" — which is task 5's machinery,
which is the third time these two tasks touch.

**Test it on `niraireading` (the friend's hotel), never on `nirai1` first.**

### 3.2 · Task 5, DELETE WITH RESTORE (48.4)

Answering the four questions directly, from the code:

**Where does the snapshot live?** S3, `deleted-hotels/{handle}-{YYYYmmdd-HHMMSS}.json`,
one JSON object per deletion, in the uploads bucket. Versioning is ON and
SSE-AES256 is ON (`infra/s3.tf`). It is written by `deletion.archive()` before
anything is removed, and the delete refuses outright if the archive fails —
that part of the design is right and should be kept exactly.

**How big?** Unmeasured, and it must be measured before restore is designed.
`json.dumps(dump, default=str)` of every row of ~60 tables is roughly 2–5× the
on-disk size, and it is built entirely in memory on a **t3.micro** before being
uploaded — which is the real risk, not the storage cost. A busy restaurant with
a few hundred thousand rows is a single-digit-to-low-tens-of-MB file and fine;
the failure mode is a large tenant OOM-ing the container mid-archive and the
delete then correctly refusing, forever. The database-engineer takes the number
from `deletion-preview` on the live fleet as the first action of this task, and
if any hotel is large the archive streams per-table objects instead of one blob.

**How long is it kept?** Today, **forever** — there is no lifecycle rule on the
bucket. `deletion.py`'s docstring says "permanent still has a way back for the
ten minutes after somebody realises", which understates it in one direction and
creates a liability in the other: indefinite retention of a deleted UK
restaurant's staff names, salaries and phone numbers, with no stated policy, is
a GDPR problem the moment somebody asks to be forgotten. **Set a policy: 90
days, then expire the object; the `deleted_hotels` ledger row survives forever
because it contains no personal data.** That also bounds the cost.

**What is the restore restoring INTO?** This is the question that decides the
whole design, and the honest answer is **the same hotel id**. Every foreign key
inside the dump references the old ids; the S3 document keys are
`{hotel_id}/...`; the handle, the subdomain and every user row key off it.
Restoring into a NEW id means rewriting every FK in the file — which is exactly
task 4's copier, and is why task 4 comes first. So:

- restore targets the ORIGINAL `hotel_id`;
- it REFUSES if that id currently exists (never merge into a live hotel — a
  partial merge is unrecoverable and looks fine);
- restoring into a new id is a second, later capability, and it is the copier.

For **48.4a** specifically (wipe but keep the owner login) the snapshot is not
optional and not the same as the existing one: the hotel row and the owner user
survive, so the archive must record exactly the set that was removed, and the
restore must put it back alongside rows that were never gone. Every id is
still valid, which makes this the EASIEST restore to get right and the right
one to build first.

**And before any of that: `archive()` must use `_delete_plan()`.** As shown in
§1, today it archives from a stale hand-written list and silently omits chats,
chat messages, the audit trail, `ai_usage` and at least five other tables that
the purge does destroy. A restore built on that archive is a restore that
quietly loses data, which is worse than no restore at all, because he will
trust it.

**Who may press it.** 48.4a is described from the tenant's seat ("i need delete
all datas feature"). A tenant-side button that empties a restaurant needs more
than the typed-handle pattern: owner role only, password re-entry, and the
restore path must be reachable by him in the Control Room within minutes — not
a support ticket. 48.4b's "make it dangerous" is satisfied by
`deletion.py`'s existing reasoning (type the name, see the counts, no
checkbox); copy it rather than invent a second style.

### 3.3 · 48.2e — "AI can write" is NOT a policy change. State that plainly.

My brief for this task said the assistant has no write tools by design. **That
is not what the code says**, and getting this wrong in either direction is
expensive, so here it is explicitly:

`backend/app/assistant/actions.py` opens with: *"The model never mutates the
database directly. It calls a propose_* tool, which validates + normalises the
request and returns a human-readable proposal (no write). The UI shows a
confirmation card; only when the user confirms does the frontend call
/assistant/act, which EXECUTES here via the normal services, scoped to the
user's hotel + RBAC, and audit-logged. Every action returns an ``undo`` token."*

That IS the law — *it proposes, the server authorises* — and it is already
implemented, with 13 propose tools, RBAC filtering (`tools_for`), audit and
undo. **48.2e does not ask for permission the assistant lacks.** It asks for a
different SHAPE of that permission: one proposal covering many rows.

That is still a real change in blast radius and must be stated rather than
slipped in, because a batch write is a genuinely different risk from N single
writes:

- one careless Apply can now create forty suppliers instead of one;
- the model's extraction errors arrive in bulk, so a misread column becomes
  forty wrong rows;
- and undo, which today reverses one action, must reverse the whole batch as
  one or it is not an undo.

**The conditions I would require before shipping a batch write** (these are the
statement, and the security-engineer signs them off):

1. The confirmation card ENUMERATES every row. A card saying "add 40 vendors"
   with the list collapsed is a checkbox wearing a list's clothes.
2. The duplicate preview (48.2f) is INSIDE that card, not after the write —
   which is why 48.2f belongs to task 1 and this task inherits it.
3. One undo token reverses the entire batch atomically.
4. A hard cap on batch size, enforced server-side, with a clear message above
   it — bulk beyond that goes through the file importer, which has a preview
   and a validation report.
5. Unchanged: RBAC per row, hotel scoping per row, an audit event per row.
6. Unchanged and non-negotiable: **the model still never writes.** It proposes
   a batch; the server authorises the batch.

## 6 · RISKIER THAN IT SOUNDS

Five things in this batch are larger or sharper than their sentence suggests.

1. **"Delete everything, with a way back" is not two features, it is one, and
   the way back does not exist.** The archive he would be relying on is
   incomplete against its own purge today — chats, audit history and AI usage
   are destroyed and never written to S3. If 48.4 shipped as a wipe plus the
   existing archive, the first restore would look successful and quietly return
   a hotel missing several tables. **The archive fix must ship before the wipe
   does**, and it is the one item in this whole plan I would not let slip.

2. **"COPY a hotel — everything — to a new email" can leak data between tenants
   without erroring.** A single unremapped foreign key leaves the new
   restaurant pointing at the old one's row. Nothing turns red. It will be
   discovered months later as a pricing or stock anomaly. This is the reason
   task 4 gets both an architect and a security-engineer before code, and the
   reason its acceptance test is a database scan rather than a screenshot.

3. **"AI can write" is already true, and the risk is the batch, not the
   writing.** Do not let this be recorded as "we gave the AI write access" — it
   has had authorised, confirmed, audited, undoable write access for months.
   What changes is one Apply creating forty rows from one model extraction. See
   the six conditions in §3.3; they need saying out loud once, now, rather than
   being discovered as an incident.

4. **Onboarding "completely missing" is a routing bug wearing a rebuild's
   clothes.** 601 lines exist and return 200. He is right that it is missing in
   every way that matters to him, and right to want it rebuilt — but if we only
   rebuild the page and not `frontend/lib/auth.tsx:110`, the new page will be
   just as unreachable and the fault will read as unfixed. **Ship the routing
   first, separately, so at least one half is provably solved early.**

5. **The runway is 85 days and §41 is 39 screens.** $85.83 of credit at a
   measured ~$1.00/day. §41 and §42 are the two biggest blocks of remaining
   work and both are explicitly gated by him behind "finish the existing
   pending tasks". At some point that arithmetic has to be a conversation, not
   a surprise — and three free budget fixes (43.6, 43.7, 43.10) should happen
   this week so that when the credits do run out, something actually tells us.
