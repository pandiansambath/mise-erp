## 0 · SERIOUS — purchasing basket (staff are blocked)

> "we got a serious bug we need to solve this on priority — staff are getting
> affected... you can notice that basket is missing in 2nd pic. if i move cursor
> that basket is flickering and hidden. somehow i tried and clicked basket, now
> when i click submit indent nothing is happening. please use playwright to test
> the functionality. this is real bug."

Two separate faults, both mine, both found in the code before touching the site.

- [x] **0.1 "Submit indent" does nothing.**
      `SheetPopup` renders through `createPortal(ui, document.body)`. A portal
      keeps the REACT tree but not the DOM tree, and `<button type="submit">`
      submits the form it is a DOM descendant of. The button is passed down
      `<form>` → `OrderFlow footer` → `BasketSheet footer` → portal, so in the
      DOM it is a child of `<body>` with no form owner at all. Clicking it is a
      no-op — exactly what he saw. Fixed with the HTML form-owner attribute
      (`<form id>` + `form="…"` on the button), which works across ancestry.
      *Broke when I extracted SheetPopup to a portal; nothing was checking it.*
- [x] **0.2 Basket disappears / flickers.**
      The drag clamps against `window.innerWidth`, which INCLUDES the vertical
      scrollbar, so the basket can be parked in the strip under it. A `fixed`
      element there overflows the page — which is the horizontal scrollbar that
      appears in his 2nd and 3rd screenshots and not the 1st. The remembered
      position was also never re-checked: it is read from localStorage and
      applied whatever the window is now. Clamp on the client width, re-clamp on
      load and on resize.
- [x] **0.3 Playwright proof** of add → basket → submit → indent created.

It was never a scrollbar. `html { scrollbar-gutter: stable }` reserves ten
pixels on the right for all time, so no page jumps sideways when it grows tall

restaurant's front door.

the reservation and a visible seam to lose by it. The door now releases the
gutter while it is on screen and takes the full width.

Worth noting how it was found: the automated check passed. It measured
`scrollHeight - clientHeight = 0` and called the page clean, and it was right —
the page genuinely does not scroll. The seam was only ever visible in the
screenshot.

      THE FLOOR ALONE WOULD HAVE BEEN WORSE. `max(net, 0)` stops the negative
      payslip and silently forgives the debt: the advance gets marked recovered,
      the £3,500 never comes back, and nothing records that it happened. So the
      calculator now returns what was actually TAKEN and what is STILL OWED, and
      `salary_advances` gained an `amount_recovered` column to hold the
      remainder — an advance is not all-or-nothing and never was.
      Penalties come off before advances: a penalty is a charge for this period,
      an advance is our own money and can wait one. 18 assertions in
      `tests/test_payroll_deductions.py`, including the exact production row.

- [x] **The dry run showed a figure the real run would not produce.**
      `preview_payroll` filtered advances on `is_deducted` alone;
      `process_payroll` also filtered `deduct_period`. So the preview summed
      EVERY outstanding advance from every period and the confirmation screen
      showed a deduction, and a net, that the run then did not produce. A dry run
      that disagrees with the run is worse than none, because its number is the
      one somebody approves. Both now call one `pending_advances()`.

- [x] **A custom-range run could never be approved.** `2026-07-01→2026-07-07`
